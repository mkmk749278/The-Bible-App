# Project audit — September 2026

Scope: all app code (~28k lines of Kotlin, 100+ test classes), build and CI config,
bundled assets, store and privacy documents, measured against the Owner Brief in
`CLAUDE.md` and Google Play policy as of 24 Sep 2026.

Method: every source file was read; the debug build, the minified release build, the
unit tests (baseline: 452, all passing) and lint (baseline: 0 errors, 97 warnings) were run
locally; the five bundled Bibles were compared against each other; the live Free Use
Bible API catalog was checked.

## Open — needs an owner decision (highest priority first)

1. **Treat the Gemini API key as already public, then rotate and lock it down (P0, owner
   action in Google Cloud).** The repository is public. The key is compiled into the release
   APKs on the GitHub Releases page and into the debug APK that `android-build.yml` uploads
   as an artifact on every PR, and anyone can extract it from either. Create a new key and
   restrict it to Android apps, using package `com.manna.bible` and the **Play app-signing**
   SHA-1 from Play Console → App integrity (the app now sends the headers this needs); add
   the upload-key SHA-1 too if you install CI-signed APKs directly. Restrict it to the
   Generative Language API and set a daily quota. Swap it into the `GEMINI_API_KEY` secret,
   test once, then delete the old key. Consider not injecting the key into PR debug builds.
2. **Move the key to a paid (billing-enabled) project and re-submit Play Data Safety (P0).**
   On the free tier Google may use prompts, including crisis and persecution text, to
   improve its products, with human review. Then submit the form per
   `docs/play-store/02-data-safety-and-rating.md` and republish the hosted privacy policy
   (`docs/privacy-policy.html`).
3. **Stealth Mode: at-rest encryption is not implemented (P1).** `AesGcm` exists but is
   unused. The launcher icon and name still say "Manna". Decide whether to (a) encrypt notes
   and prayers under a PIN-derived key (this trades away widget and reminder access and
   makes a forgotten PIN mean lost data), and (b) add a disguised `activity-alias` icon.
4. **Download failure policy (P1).** A network error mid-download deletes all completed
   books (Req 5.7). On flaky rural networks, keeping the finished books and auto-retrying
   would save hours. This needs a spec change.
5. ~~**Telugu IRV versification (P1).**~~ **Done (owner approved):** the Telugu IRV
   merges 103 verses into their neighbour (e.g. 1 Cor 4:15–16 stored as verse 15). The new
   `MergedVerses` helper resolves such references to the verse that carries them in every
   lookup path and in the reader's scroll, jump-highlight and annotation flags.
   `BundledMergedVersesTest` proves every WEB verse now resolves in all four Indian
   editions except Romans 14:24–26, which they print as 16:25–27. Residual limits: the
   shown reference keeps the requested number (e.g. "4:16" over the 15–16 text), and
   Mark 9:44/46 are genuine omissions in the Telugu IRV, so they resolve to the adjacent
   verse.
6. **Theme default (P2).** The code defaults to dark (commit 2eb5698), but the UX
   directive in CLAUDE.md says "light by default". Pick one and align the other.
7. **Native-speaker review (P2)** of the new crisis strings (hi/ta/te/ml). Also update the
   localized store listings, which still say the network is used only to "explain a
   passage".
8. **Lock-screen and Bluetooth media controls (P2).** Add a Media3 `MediaSession`.
9. **Dependency refresh (P2).** Compose BOM 2024.12, Hilt 2.52 (forces Kotlin metadata 1.9
   via `languageVersion`), Room 2.6.1, Media3 1.4.1, and the experimental
   `aicore 0.0.1-exp02` all have newer releases. Lint lists 42.
10. **Small items (P3).** `AssetLiturgyProvider` uses `runBlocking` on first access. The WEB
    Bible has five blank, text-critically omitted verses (Luke 17:36, Acts 8:37, 15:34,
    24:7, Rom 16:25) that render as empty rows. There are 41 unused string/colour
    resources.
